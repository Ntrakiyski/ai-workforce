# Build and operate OIX apps

Source baseline OIX-APP-001, VERIFIED_SOURCE for OIX 0.8.0. Python 3.11+ and an Apps-capable Open WebUI deployment are prerequisites. This SDK builds an independently running app with a client bound to the originating installation. Provider settings, workspace model administration and native Function installation belong to WebUI's own administration surfaces. [SDK package](https://github.com/open-webui/oix/blob/6134c423f553aa9886f2de6ad822f46fb51239e0/pyproject.toml#L1-L20) · [Runtime client](https://github.com/open-webui/oix/blob/6134c423f553aa9886f2de6ad822f46fb51239e0/README.md#runtime-client)

1. Pick the interaction. For explicit mentions use `channel.mention` with `channels:mentions:read`. For all ordinary message events request `channels:messages:read`. For public channel replies add `channels:messages:write`. Describe who may cause each business operation. A verified event identifies its origin. Apply authorization separately to the installation, channel, actor and operation. [Events and scopes](https://github.com/open-webui/oix/blob/6134c423f553aa9886f2de6ad822f46fb51239e0/README.md#scopes)
2. Instantiate `App` with a stable manifest ID, display name and requested scopes. Register async handlers with `@app.on(...)`. Send a message-event reply using `await event.reply(...)`. Keep the installation's client and IDs together. For a button, register the action ID and use its supported response form. Route each logical trigger once when an interaction also produces a message event. [App and handlers](https://github.com/open-webui/oix/blob/6134c423f553aa9886f2de6ad822f46fb51239e0/README.md#events-and-replies)
3. Provision a persistent Ed25519 signing key and API key in the app's secret store. Only the API key is entered in WebUI. For an authorized staging install, enable Apps and Channels, connect using the app endpoint, review scopes and invite the app to the intended channel. Check reachability **from the WebUI service to the app** and proxy WebSocket support. For private development, scope the allowed private origin to the intended app, taking container addressing into account. [Connect and local development](https://github.com/open-webui/oix/blob/6134c423f553aa9886f2de6ad822f46fb51239e0/README.md#connect-to-open-webui)
4. Plan for a disconnect between submitting work and seeing the outcome. Use timeouts. Acknowledged ordinary events can be lost on process failure. For consequential delayed actions, persist accepted work and an idempotency key, recheck authorization before the action, and reconcile ambiguous results before retrying. A timed-out send may already have produced a message. [Delivery and admission](https://github.com/open-webui/oix/blob/6134c423f553aa9886f2de6ad822f46fb51239e0/README.md#events-and-replies) · [Client errors](https://github.com/open-webui/oix/blob/6134c423f553aa9886f2de6ad822f46fb51239e0/README.md#runtime-client)

## Verify a channel integration

Use a dedicated staging channel with an allowed user and a restricted user. Exercise a matching trigger, an unrelated message, the restricted user, and dependency failure. Confirm the correct reply channel/thread, bounded response time and absence of a downstream call for rejected triggers. Remove the channel invitation or revoke the grant and verify subsequent access stops. Test a second installation if the service is shared. For rollback disconnect the test installation and restore prior configuration.

For n8n-backed status requests, the repository example lives under `joint/homelab-status/`. Read its actual command, scope and allowlist before testing. Keep returned status distinguishable from transport or authorization failures.
