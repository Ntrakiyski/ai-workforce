# n8n 2.47.7: First Verified Internal Findings

**Version:** `2.47.7`. **Commit:** [`d4dcb1b152a98fc31ea7c4ee6aecdc45c5c88063`](https://github.com/n8n-io/n8n/commit/d4dcb1b152a98fc31ea7c4ee6aecdc45c5c88063). **Inspected:** 2026-11-14. **Evidence class:** VERIFIED_SOURCE. **Scope:** selected source files only. No runtime instance executed.

## F-001: Structural validation has a narrow scope

[`workflow-structure-validation.ts`](https://github.com/n8n-io/n8n/blob/d4dcb1b152a98fc31ea7c4ee6aecdc45c5c88063/packages/workflow/src/workflow-structure-validation.ts) defines a Zod `workflowStructureSchema` containing `nodes` (array) and `connections` (object mapping). It checks:

- Every node has a nonempty `name`, nonempty `type`, and a numeric two-element `position` tuple.
- Optional `parameters` is a record; optional `id` is a string; optional `typeVersion` is numeric.
- Node names must be unique; nonempty supplied node IDs must be unique.
- Connection sources and targets must reference existing node names.
- Connection entries carry nonempty `node`, nonempty `type` and nonnegative integer `index` no greater than the defined limit.
- Unused output buckets may be `null`.

The file explicitly states structural validation **does not check installed node types, parameter validity, credentials or activation readiness**. Therefore, a structural pass is only gate 1, never acceptance of the workflow as ready.

**Important nuance:** `INode` in [`interfaces.ts`](https://github.com/n8n-io/n8n/blob/d4dcb1b152a98fc31ea7c4ee6aecdc45c5c88063/packages/workflow/src/interfaces.ts) requires `id`, `typeVersion`, and `parameters` in its TypeScript shape, while *structural input validation* treats them as optional. This is not a contradiction: persisted/typed workflow objects and permissive initial structural validation serve different purposes. Whether an endpoint will supply defaults must be checked per endpoint and import path.

## F-002: Connection graph representation

[`interfaces.ts`](https://github.com/n8n-io/n8n/blob/d4dcb1b152a98fc31ea7c4ee6aecdc45c5c88063/packages/workflow/src/interfaces.ts) declares `IConnections`, `INodeConnections` and `IConnection` (target `node`, destination input `type`, destination input `index`). This model keys outgoing connection arrays by **source node name**, then by output connection type and source output slot. The entry points to the destination node and input slot.

Conceptual example only:

```json
{
  "connections": {
    "Fetch": {
      "main": [[{"node":"Normalize","type":"main","index":0}]]
    }
  }
}
```

This is a **graph fragment**, not a complete import-ready workflow.

[`map-connections-by-destination.ts`](https://github.com/n8n-io/n8n/blob/d4dcb1b152a98fc31ea7c4ee6aecdc45c5c88063/packages/workflow/src/common/map-connections-by-destination.ts) defines `MAX_CONNECTION_INDEX = 1000` and a separate `MAX_DESTINATION_INPUT_SLOTS = 100000`. Guard graph size and input-index abuse; do not assume arbitrary indices are harmless.

## F-003: Node fields and failure controls

`INode` in `interfaces.ts` includes `id`, `name`, `typeVersion`, `type`, `position`, `parameters`; optional `credentials`, `disabled`, `retryOnFail`, `maxTries`, `waitBetweenTries`, `alwaysOutputData`, `executeOnce`, and `onError`.

`OnError` is declared as:

```ts
type OnError = 'continueErrorOutput' | 'continueRegularOutput' | 'stopWorkflow';
```

These are actual enum values in the tagged code; their effective runtime behavior, interactions with `continueOnFail`, and edge cases still need specific execution tests. **Do not assume enabling continue creates a safe recovery strategy.**

## F-004: Node type descriptions carry versioned properties

`INodeTypeDescription` includes `version`, `defaults`, `inputs`, `outputs`, `properties`, optional `credentials` and potentially other operation-specific metadata. A workflow generator must discover node `typeVersion`, operation/property visibility and required fields from the target-compatible node definition—not from a static prompt.

Inspect [`interfaces.ts`](https://github.com/n8n-io/n8n/blob/d4dcb1b152a98fc31ea7c4ee6aecdc45c5c88063/packages/workflow/src/interfaces.ts) and each node's own declared properties before hardening a node recipe.

## F-005: Trigger presence is a separate validation concern

[`workflow-validation.ts`](https://github.com/n8n-io/n8n/blob/d4dcb1b152a98fc31ea7c4ee6aecdc45c5c88063/packages/workflow/src/workflow-validation.ts) contains `validateWorkflowHasTriggerLikeNode`, which looks for a non-disabled recognized node with a `poll`, `trigger` or `webhook` handler. This is distinct from graph-structure checks; it is one component of activation/publish readiness, not an exhaustive readiness guarantee.

## F-006: Workflow metadata is richer than nodes and edges

`IWorkflowBase` includes `id`, `name`, `active`, `isArchived`, lifecycle dates, `nodes`, `connections`, optional `settings`, `staticData`, `pinData`, and version metadata. `IWorkflowSettings` includes error workflow, timezone, execution timeout, saving execution data, caller policy and MCP availability, among others.

It is **incorrect to infer that all fields in `IWorkflowBase` are mandatory in every workflow JSON import or API create payload**. The next research milestone must compare actual contracts by entry point: clipboard, editor import, Public API create/update, portable packages, Git push/pull and execution serialization.

## F-007: Item linkage is a runtime semantic requirement

Official [item-linking documentation](https://docs.n8n.io/data/data-mapping/data-item-linking/item-linking-node-building/) states that programmatic nodes can need explicit `pairedItem` metadata to preserve provenance of output items. Missing links can break downstream expressions. For declarative-style nodes, n8n handles linking in the documented cases. This behavior deserves a dedicated execution fixture.

## F-008: Source-control deployment is not publication

The official [environments tutorial](https://docs.n8n.io/administer/use-source-control-and-environments/tutorial-create-environments-with-source-control.md) says the Git push uses the **saved**, not the published workflow version, and publication on the remote instance is separate. The tutorial also identifies Business/Enterprise availability for native source-control environments. Do not design release automation assuming Git pull automatically publishes a working production version.
